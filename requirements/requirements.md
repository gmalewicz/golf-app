| CR-05 | Update the player's WHS handicap index (`whs` in `Player`) from the Polish Golf Association (PZG) service by a scheduled job. Add an optional `pzgId` (Long) field to `Player` (database column, nullable); players without it are skipped. The functionality shall be switched on and off by the configuration parameter `pzg.enabled` (boolean, in `application.yml`, bound through a `@ConfigurationProperties("pzg")` class like the other `*Config` classes, default `false`, overridable by the `pzg.enabled` property supplied by the deployment, like the other secrets and settings); no code change or redeployment of the front end is needed to change it. When it is `false` the PZG service is never called, no PZG login is made and `whs` is not modified; when it is `true` the job updates all players that have `pzgId` set. The job runs every day at 3:00 a.m. (Europe/Warsaw time zone); the sign-on does not call PZG and is not affected in any way. The PZG service base URL, user name and password shall be configuration properties of the same `pzg` group (`pzg.url`, `pzg.username`, `pzg.password`). The credentials shall be supplied by the deployment as the `pzg.username` and `pzg.password` properties (the Kubernetes secret, like `spring.mail.username`); `application.yml` only holds `replace_it` placeholders. During a run the backend shall log in to the PZG service (`POST /api/_account1/auth/login`, body `{"email","password"}`, the response contains `token`) with a technical account whose credentials are taken from configuration or environment variables (never stored in the repository), then for each player call `GET /api/_account1/member/get_profile?id={pzgId}` (Bearer token) and store `member.hcp` in `Player.whs`. The token shall be cached and a new login performed when it expires (HTTP 401). The PZG call has a short timeout (`pzg.timeoutMs`, default 3000 ms). An error for one player (member not found, invalid or out of range (-5 to 54) value) is logged and the existing `whs` value of that player is kept, and the job continues with the next player; the job is aborted (and logged) after 5 consecutive failures, e.g. when the service is unavailable. Only the `hcp` value is read from the response; the photo and the other profile data shall be ignored and not stored. |

After a successful response the table cell is updated without reloading the list and the success alert "The player <nick> PZG ID has been successfully updated" is shown; on error the cell is left unchanged. The endpoint `GET /rest/PlayerRoundCnt` (and `PlayerRndCnt` model) shall also return `pzgId` (Long, nullable). |
| CR-07 | In the Player management page (admin, `players.component`) add a new "down arrow" icon button (Font Awesome `faArrowDown` icon in a Bootstrap link-style button, with the tooltip "Update HCP from PZG") placed right next to the PZG ID value in the "PZG ID" column (see CR-06). The button is displayed only for a player that has `pzgId` set (not null); for a player without `pzgId` it is not rendered. Clicking the button must not open the PZG ID edit dialog (the click shall not propagate to the cell). The button is disabled while the request for that player is in progress. Clicking it triggers an immediate, on-demand update of the handicap of that single player from the Polish Golf Association (PZG) service, using the same logic as the scheduled job from CR-05 (login with token caching and re-login on HTTP 401, `GET /api/_account1/member/get_profile?id={pzgId}`, only `member.hcp` is read, value range -5 to 54, timeout `pzg.timeoutMs`) and storing the result in `Player.whs`. The front end calls the new endpoint PATCH /rest/PlayerWhsFromPzg with body `{"id": <playerId>}`, available to the ADMIN role only. The PZG calls (login and get_profile) are retried once after 500 ms when PZG answers with a 5xx error or does not answer in time; only then the update is treated as failed. The on-demand update is executed regardless of the daily schedule, but it still honours the `pzg.enabled` switch: when it is `false` the PZG service is not called, `whs` is not modified and the endpoint returns 409 (the front end shows the error alert "PZG integration is disabled"). The endpoint returns 404 when the player does not exist, 400 when the player has no `pzgId`, 502 when the PZG service is unavailable, times out or returns no member / an invalid or out of range `hcp` (the existing `whs` is then kept and the error is logged), and 200 with the body `{"id": <playerId>, "whs": <new value>}` on success. Only `Player.whs` is modified; no other player field is changed and the player cache is evicted the same way as in the scheduled job. After a successful response the WHS value of that player in the table (if displayed) is updated without reloading the list and the success alert "The player <nick> handicap has been successfully updated from PZG to <whs>" is shown; on error the value is left unchanged and the error alert is shown. |
